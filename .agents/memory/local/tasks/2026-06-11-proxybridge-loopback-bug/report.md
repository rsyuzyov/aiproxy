# ProxyBridge: loopback-трафик к локальным сервисам рвётся при активном перехвате

**Статус:** баг подтверждён, первопричина локализована, фикс не сделан (отдельный проект).
**Дата:** 2026-06-11. **Версия ProxyBridge:** V4.0-Beta.
**Апстрим:** https://github.com/InterceptSuite/ProxyBridge (последний релиз ~4 мес назад, ответа ждать не стоит → форк/самостоятельный фикс).

---

## 1. Суть проблемы (TL;DR)

Когда ProxyBridge активен (перехватывает трафик через Netfilter **NFQUEUE на цепочке OUTPUT**),
HTTP-запросы к **локальным сервисам на `127.0.0.1`**, при обработке которых сервер делает
нетривиальную работу (большой ответ / SSR self-fetch), **виснут** (timeout, часто 0 байт ответа).
Мелкие/быстрые запросы к тем же портам проходят мгновенно. **Внешний трафик работает нормально.**

Критично: баг проявляется **даже когда у ProxyBridge нет ни одного правила и не задан прокси**
(чистый pass-through). То есть виноват **сам факт NFQUEUE-перехвата**, а не PROXY-действие.
Снять можно только `ProxyBridge --cleanup` (убрать правила) или остановкой процесса — отключением
правил в GUI/конфиге это НЕ лечится.

Симптом на уровне сети: `curl → 127.0.0.1:<порт>` застревает в **SYN-SENT** (loopback-хендшейк не
завершается), хотя в правилах ProxyBridge есть `*:127.0.0.1:*:BOTH:DIRECT`.

---

## 2. Как ProxyBridge ставит перехват

При старте процесс добавляет в OUTPUT (видно через `iptables-save | grep -i nfqueue`):
```
-A OUTPUT -p tcp -j NFQUEUE --queue-num 0
-A OUTPUT -p udp -j NFQUEUE --queue-num 0
```
Особенности:
- **нет исключения `-o lo`** → loopback-трафик тоже уходит в очередь;
- **нет `--queue-bypass`** → если демон умрёт, трафик встаёт (fail-closed, это by design);
- ip6tables NFQUEUE-правил нет (IPv6 не перехватывается).

`ProxyBridge --cleanup` удаляет эти правила. Очередь: `cat /proc/net/netfilter/nfnetlink_queue`
(колонки: `queue# peer_portid queued copy_mode copy_range q_dropped user_dropped id_seq 1`).
В сбойном состоянии очередь **здорова**: один процесс привязан (`peer_portid`≠0), `q_dropped=0`,
`user_dropped=0` — то есть дело не в переполнении очереди, а в логике обработки loopback.

## 3. Воспроизведение «с нуля» (без участия пользователя)

### 3.1. Окружение

Свежий **Debian 13** (glibc ≥ 2.38; ProxyBridge на Debian 12 не запустится). Подойдёт LXC/VM.
Развернуть три локальных HTTP-сервиса (один Go, два Next.js — чтобы покрыть и статику, и SSR):

```bash
# Вариант А — через установщик aiproxy (даёт ровно ту же связку, что у репортера):
wget -O- https://raw.githubusercontent.com/rsyuzyov/aiproxy/master/install.sh \
  | bash -s -- --cliproxy --9router --omniroute --proxybridge -y
# Поднимутся: cli-proxy-api :8317 (Go), 9router :20128 (Next.js), OmniRoute :20129 (Next.js),
# ProxyBridge (бинарь + systemd-юнит proxybridge).
```

```bash
# Вариант Б — минимальный, без aiproxy: любой локальный сервер с тяжёлым ответом.
# (гипотеза репро; стоит проверить — должно вешаться так же, т.к. баг в самом перехвате)
dd if=/dev/urandom of=/srv/big.bin bs=1M count=3
cd /srv && python3 -m http.server 8080 --bind 127.0.0.1 &
```

### 3.2. Включить перехват ProxyBridge

Достаточно запустить ProxyBridge — даже **без правил и без прокси**:
```bash
systemctl start proxybridge        # или: /usr/local/bin/ProxyBridge &
iptables-save | grep -i nfqueue    # убедиться, что NFQUEUE-правила встали
```
(Опционально — как у репортера, catch-all через внешний SOCKS5; на репро не влияет:
`--proxy socks5://HOST:PORT --rule '*:127.0.0.1:*:BOTH:DIRECT' --rule '*:*:*:BOTH:PROXY'`.)

### 3.3. Тест

```bash
# Тяжёлые роуты (SSR / большой файл) — ВИСНУТ:
for u in http://127.0.0.1:8317/management.html \
         http://127.0.0.1:20128/dashboard \
         http://127.0.0.1:20129/login \
         http://127.0.0.1:8080/big.bin ; do
  curl -sS -o /dev/null -w "%{url_effective} -> %{http_code} (%{time_total}s)\n" --max-time 12 "$u"
done

# Мелкие роуты тех же портов — мгновенно:
for u in http://127.0.0.1:8317/ http://127.0.0.1:20128/api/health http://127.0.0.1:20129/ ; do
  curl -sS -o /dev/null -w "%{url_effective} -> %{http_code} (%{time_total}s)\n" --max-time 6 "$u"
done

# Внешний трафик — работает:
curl -sS --max-time 10 https://ifconfig.me ; echo

# Поймать SYN-SENT на loopback во время висяка:
( curl -s -o /dev/null --max-time 12 http://127.0.0.1:20128/dashboard & )
sleep 2; ss -tanp state syn-sent
```

### 3.4. Доказательство, что виноват именно перехват (A/B)

```bash
/usr/local/bin/ProxyBridge --cleanup     # снять NFQUEUE-перехват
# повторить тесты из 3.3 → ВСЕ панели отвечают 200 за <0.03с
systemctl restart proxybridge            # вернуть перехват → снова виснут
```

## 4. Что ПРОВЕРЕНО и ОТБРОШЕНО (чтобы не повторять)

- **Не матчинг адреса** (`::ffff:127.0.0.1`, dual-stack). Сервисы слушают dual-stack, loopback
  в `ss` виден как `[::ffff:127.0.0.1]`. Но мелкие роуты на ТОМ ЖЕ сокете/адресе работают — значит
  адрес матчится; будь иначе, висело бы всё на порту.
- **Не DNS-via-proxy.** `dns=0` (`--dns-via-proxy false`) + рестарт → панели всё равно висят.
- **Не размер очереди.** `q_dropped=0`, `user_dropped=0`, один инстанс. Очередь обслуживается.
- **Не баги бинарей сервисов.** Падают ТРИ разных стека (Go + 2×Next.js) одновременно и только при
  активном перехвате; при `--cleanup` все работают. (Изначально баг ошибочно списывали на бинари.)
- **Не специфично для PROXY-действия.** Репро есть и при нуле правил/без прокси (default DIRECT).

## 5. Провалившиеся обходы (не предлагать как фикс)

- `iptables -I OUTPUT 1 -o lo -j ACCEPT` — «чинит» панели ОБМАНОМ: ProxyBridge реагирует на правку
  своей OUTPUT-цепочки тем, что **снимает свой NFQUEUE-перехват** → внешний трафик уходит напрямую
  (утечка мимо прокси!). То есть ручная правка цепочки при живом ProxyBridge недопустима.
- `iptables -I OUTPUT 1 -o lo -p tcp -m multiport --ports 8317,20128,20129 -j ACCEPT` — ProxyBridge
  терпит (NFQUEUE цел), но висяк НЕ лечит.
- Отключение всех правил в GUI/`config.ini` (`enabled=0`) — перехват остаётся включённым.

## 6. Вероятная первопричина и направление фикса

ProxyBridge тянет в userspace и реинъектит **все** OUTPUT-пакеты, включая loopback (`lo`). Даже при
action=DIRECT реинъекция/обработка loopback-flow ненадёжна: хендшейк к локальному сервису застревает
в SYN-SENT, нетривиальные ответы не доставляются.

**Где смотреть в исходниках:** каталог `Linux/` репозитория ProxyBridge — код установки
iptables/nft-правил (там, где добавляется `OUTPUT ... NFQUEUE`) и основной цикл вердиктов NFQUEUE.

**Кандидат фикса (стандартная практика прозрачных прокси, как в redsocks):** исключать loopback
из перехвата на этапе установки правил, т.е. добавлять ПЕРЕД NFQUEUE-правилами что-то вроде
`-A OUTPUT -o lo -j ACCEPT` (или `-d 127.0.0.0/8 -j RETURN`), и симметрично для ip6tables. Loopback
проксировать незачем — это безопасно. Альтернатива — в самом цикле вердиктов сразу выдавать ACCEPT
для пакетов интерфейса `lo`/адресов `127.0.0.0/8`/`::1`, не таща их в полную обработку.

После любого фикса проверить: (а) панели из 3.3 отвечают мгновенно; (б) внешний трафик всё ещё идёт
через прокси (exit IP = адрес прокси); (в) NFQUEUE-правила на месте (перехват внешнего жив).

## 7. Доступ к референс-окружению (живой контейнер репортера)

Опционально, если нужен уже настроенный пример (рекомендуется всё же пересоздавать с нуля по п.3):
- Proxmox-хост: `ssh srv-hv1.ag.local`
- Контейнер: `pct exec 107 -- bash -lc '<команда>'` (имя aiproxy1, Debian 13).
- ProxyBridge там стоит из aiproxy; конфиг `/etc/proxybridge/config.ini` (единый для GUI и службы).
- ⚠️ Креды внешнего прокси из `[SETTINGS]` для репро НЕ нужны (баг есть и без прокси) — не выносить.

## 8. Грабли для агента (операционное)

- ⚠️ **Не убивать ProxyBridge через `pkill -f <pattern>` по ssh** — паттерн совпадает с собственной
  командной строкой и убивает шелл (exit 137). Только `kill <PID>`.
- GUI и служба взаимоисключающие: `gui-wrapper.sh` стопает службу на старте ProxyBridgeGUI и
  запускает на выходе. `proxybridge.service=inactive` при открытом GUI — норма.
- Вернуть рабочее состояние после экспериментов: `systemctl restart proxybridge`
  (проверить: exit IP снова = прокси, мелкие роуты отвечают).
- strace в LXC обычно не цепляется (ptrace закрыт) — диагностировать через `ss -tanp`.
